## 振り返り（Gold V1英語版 Choice / Score の動き）

| 試したこと | 効果 |
|---|---|
| pooling（mean） | 訓練ドメインで小改善。Goldへの効果は測れず |
| bugzilla severity 追加 | bugzilla内の順位は改善（τ+0.42）。Gold Scoreには載らない |
| null state 校正 | Scoreの予測幅は動かない |
| Noul warm-start | BoolQで0.63。Gold Noul 0.60〜0.65 |
| 言語（JA→EN） | Choice不変、Score微増。主因ではない |
| backbone差し替え（Instruct / Qwen3） | 順序判断で悪化 |
| 1.5B zero-shot | Choice 0.55（校正後）、Score改善せず |
| ticket_queue 追加 | 英語チケットは学べたがGoldは下がる |
| 合成データv1（Gold設問をなぞった＝規則違反） | Choice +2問（p=0.63）、Score 低下 |

共通点:
1. どの手を打っても Gold Choice は 0.35〜0.525 の帯から出ない。改善はどれも有意でない。
2. 学習した readout は、学習したタスクの選択肢の文言を覚える（言い換えで −0.13〜−0.30）。初めて見る設問・選択肢の意味を読んで答える力は付かない。
3. 凍結0.5Bは、Goldの設問をプロンプトで読ませても 0.40〜0.45 しか取れない。readout はこの上限を超えられない。
4. モデルを大きくすると少し上がる（1.5Bで0.55）。強いLLMは約1.0。差の正体はモデル自体の読解・指示追従能力。

## 結論

**現在の方針（凍結0.5B＋小さなreadoutを学習データの工夫で鍛える）では、実用水準には届かない見込みが高い。** データを足す・readoutを変える・校正する、は一通り試し、どれも有意な改善を出していない。足りないのは、任意の設問と選択肢を読んで判断する backbone の能力で、readout 側では補えない。

packing（16問で約4.6〜5倍速い）と、並べ替え・追加・削除への不変性は backbone に依存しないので、backbone を替えてもそのまま使える。

実用水準を目指すなら、次のどちらか（または両方）が必要:
- **指示追従できる大きいbackbone**（数B級のInstructモデル）を、今のpacking構造のままLM headの選択肢採点で使う。
- **backbone自体の学習**（LoRA等）を、Gold V1と無関係に作った多数（数百）の設問タイプ・毎回言い換えた文言で行う。

どちらも現環境の制約とぶつかる。環境: Apple M2、RAM 24GB、空きディスク約1.9GB（1.5Bをキャッシュしたため）。PyTorch の MPS（GPU）は使える状態だが、これまでの学習・評価はすべてCPUで回してきた（学習1回約2時間）。MPSで縮む可能性はあるが未測定。数B級のモデルは、ディスクを空けないと置けない。
